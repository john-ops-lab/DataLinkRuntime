# Engineering Rules

## General

- 优先采用简单、清晰、成熟、易维护的实现。
- 遵循 KISS 和 YAGNI，避免为尚未出现的需求提前设计复杂抽象。
- 修改代码前先阅读相关现有代码和项目文档，不要凭猜测重构。
- 尽量保持改动范围最小，避免顺手重构与当前任务无关的代码。
- 没有明确收益时，不主动引入新的框架、基础设施或依赖。

## Architecture

- 尊重项目现有架构、模块边界和领域术语。
- 不擅自改变已确认的核心架构。
- 以下变化必须先说明原因、影响和备选方案，并等待确认：
  - 核心数据模型
  - 公共 API
  - 模块边界
  - Runtime Contract
  - 安全模型
  - 持久化方案
  - 部署架构
  - 难以回退的重要技术选型

## Coding

- 代码应优先保证可读性和可维护性。
- 模块、函数和类保持职责清晰。
- 避免不必要的设计模式和抽象层。
- 避免重复业务逻辑。
- 避免无法解释用途的 magic value。
- 优先复用项目已有实现和依赖，而不是重复造轮子。
- 不提交 Secret、Token、密码、密钥或真实生产凭据。
- 代码格式、lint 和类型规范以项目配置文件为准，不在本规则中重复定义。

## Testing and Verification

任务完成前必须执行与本次修改相关的验证，包括：

- 自动化测试
- lint / formatter 检查
- 必要的类型检查
- 主要成功路径验证
- 与本次修改相关的重要失败路径验证

不能仅因为：
- 代码已生成
- 项目能够编译
- 服务能够启动

就宣称任务完成。

禁止为了让测试通过而：
- 删除有效测试
- 弱化断言
- 跳过真实失败
- 隐藏错误

如果存在未通过测试或无法完成的验证，应明确说明。

## Git

- 不直接在 main 分支上进行功能开发。
- 一个 PR 聚焦一个明确目标。
- 避免把无关修改混入当前 PR。
- 不自动合并 PR。
- 提交前检查最终 diff。
- Commit message 应简洁说明本次变更目的。

任务完成时必须总结：

1. 修改了什么；
2. 运行了哪些测试和检查；
3. 验证结果；
4. 已知限制；
5. 尚未完成或建议后续处理的事项。

## Decision Making

普通实现细节应优先选择最简单、最合理的方案自行推进，不要频繁中断开发询问。

只有当决策会显著影响架构、产品行为、安全性、公共接口或后续难以回退时，才暂停并请求确认。
