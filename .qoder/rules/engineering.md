# 工程规则

## 通用原则

- 优先采用简单、清晰、成熟、易维护的实现。
- 遵循 KISS 和 YAGNI，避免为尚未出现的需求提前设计复杂抽象。
- 修改代码前先阅读相关现有代码和项目文档，不要凭猜测重构。
- 尽量保持改动范围最小，避免顺手重构与当前任务无关的代码。
- 没有明确收益时，不主动引入新的框架、基础设施或依赖。

## 文档与规格优先级

- `docs/specs/` 主要保留历史里程碑设计；只有被索引明确标记为 Current/Target 的文件才是当前阶段规格，**不得默认把目录内文件当作当前产品合同**。
- 开始开发前必须先阅读 `docs/specs/README.md`，确认目标 Spec 的现行状态和已被替代的语义。
- 文档或实现发生冲突时，按以下优先级判断：
  1. 当前正在执行的 GitHub Issue / 里程碑合同定义本轮目标行为；
  2. 最新 `main` 的代码、API Schema、migration 与自动化测试定义当前已存在行为；
  3. 当前 `docs/zh-CN/product.md`、`docs/zh-CN/architecture.md` 及对应英文版；
  4. 当前阶段 Spec；
  5. 历史 Specs 仅作为演进背景和仍未被替代的局部合同参考。
- 历史 Spec 与后续 Issue/main 冲突时，不得擅自恢复旧设计；尤其不得从旧文档重新引入已被 M5.4 替代的 `Publish / Production Version / Production Worker / 强制 Save → Test → Publish → Start` 用户流程。
- 如果无法判断某条历史约束是否仍有效，应先检查最新代码、测试、当前产品文档和当前阶段 Issue，再决定是否需要人工确认。

## 语言与交付

- 所有面向人的内容统一使用中文，包括但不限于：项目文档、规格说明、GitHub Issue、PR 标题与描述、Code Review 说明、实施计划、任务总结、验证报告、已知限制和后续事项。
- Qoder 在执行任务、汇报进度、说明决策、提交完成总结时统一使用中文。
- 源代码标识符、类名、函数名、变量名、数据库字段名、API 路径、协议字段、第三方技术名称等工程标识保持英文，不为满足中文要求而强行翻译。
- Commit message 可保留通用英文类型前缀（如 `feat:`、`fix:`、`docs:`），其后的说明优先使用中文。
- 若引用外部英文错误信息、日志或协议原文，可保留原文，但解释与结论必须使用中文。

## 架构

- 尊重项目现有架构、模块边界和领域术语。
- 不擅自改变已确认的核心架构。
- 以下变化必须先说明原因、影响和备选方案，并等待确认：
  - 核心数据模型
  - 公共 API
  - 模块边界
  - Runtime Contract
  - 安全模型
  - 持久化方案
  - 部署架构
  - 难以回退的重要技术选型

## 编码

- 代码应优先保证可读性和可维护性。
- 模块、函数和类保持职责清晰。
- 避免不必要的设计模式和抽象层。
- 避免重复业务逻辑。
- 避免无法解释用途的 magic value。
- 优先复用项目已有实现和依赖，而不是重复造轮子。
- 不提交 Secret、Token、密码、密钥或真实生产凭据。
- 代码格式、lint 和类型规范以项目配置文件为准，不在本规则中重复定义。

## 测试与验证

任务完成前必须执行与本次修改相关的验证，包括：

- 自动化测试；
- lint / formatter 检查；
- 必要的类型检查；
- 主要成功路径验证；
- 与本次修改相关的重要失败路径验证。

不能仅因为：

- 代码已生成；
- 项目能够编译；
- 服务能够启动；

就宣称任务完成。

禁止为了让测试通过而：

- 删除有效测试；
- 弱化断言；
- 跳过真实失败；
- 隐藏错误。

如果存在未通过测试或无法完成的验证，应明确说明。

## Git

- 不直接在 main 分支上进行功能开发。
- 一个 PR 聚焦一个明确目标。
- 避免把无关修改混入当前 PR。
- 不自动合并 PR。
- 提交前检查最终 diff。
- Commit message 应简洁说明本次变更目的。

任务完成时必须用中文总结：

1. 修改了什么；
2. 运行了哪些测试和检查；
3. 验证结果；
4. 已知限制；
5. 尚未完成或建议后续处理的事项。

## 决策原则

普通实现细节应优先选择最简单、最合理的方案自行推进，不要频繁中断开发询问。

只有当决策会显著影响架构、产品行为、安全性、公共接口或后续难以回退时，才暂停并请求确认。
