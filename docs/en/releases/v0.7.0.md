# v0.7.0

This release builds on v0.6.1 with event triggers, Adapter batch operations, local code pre-review and protected PR delivery.

## Changes

- **Event triggers:** Kafka, Kubernetes, RabbitMQ and RocketMQ configuration, controls and reception records live inside the Adapter workbench. Creating or saving a source does not enable reception.
- **Durable reception:** DLR persists input and processing responsibility before acknowledging the source. Failure, deduplication, replay and recovery boundaries remain explicit. This release includes real RocketMQ account-permission validation and the RabbitMQ/RocketMQ feature-off recovery correction.
- **Batch operations:** Select up to 100 Adapters in the existing catalog. Manual mode runs once or requests cancellation for executions frozen during preparation; schedules toggle scheduling; Webhooks and event triggers toggle new reception. Saved configuration is used, drafts and accepted work are preserved, and each item has its own result.
- **Delivery:** Local OCR, verified fixes and re-review precede PR creation. The desired main protection requires four successful CI checks, an up-to-date branch and resolved discussions, and blocks force pushes and deletion, including administrators. Project rules continue to require human confirmation for high-risk changes.
- **CI reliability:** AI deadline tests wait for warmup Worker cleanup before starting deadline assertions, keeping cleanup outside the measured window.

Guides: [event triggers](../event-subscriptions.md), [batch operations](../adapter-batch-operations.md), [local review and merge policy](../../zh-CN/local-code-review.md).

## Upgrade

1. Back up the database and material data, and verify that the backup is readable. Preserve volumes, mounts, Worker runtime/recovery directories, Tokens, the Master Key and existing configuration.
2. Stop new reception and scheduling; check listener closure, unfinished executions and pending responsibility. Disabling reception preserves accepted data. Container health or an empty queue alone does not prove that responsibility is settled.
3. With writers stopped, select `v0.7.0`, build the new images with the existing configuration, run the repository's forward migrations, then start Control, Worker and Web. From v0.6.1's `0046_issue166_retire_ai_history`, migrate through `0047_issue219_subscriptions`, `0048_issue219_kubernetes` and `0049_issue219_queue_sources` to `0050_issue223_adapter_batches`.
4. Verify the schema, service/Worker readiness, saved configuration and existing data before restoring explicitly chosen schedules or reception. Event sources are disabled by default; set `DLR_EVENT_SUBSCRIPTIONS_ENABLED` in Control configuration when needed, then configure, test and enable each source separately.

Preserve source checkpoints, responsibilities and batch receipts. Legacy Kubernetes configurations without verifiable identity require an explicit new reception epoch, as described in the source guide. Before reverting application binaries, check compatibility with the schema and outstanding work. Do not automatically downgrade, restore an old database or clear volumes to erase accepted work. Test older binaries in an independent environment matching that version.

For v0.4.3 or earlier, first review the [v0.4.4 upgrade notes](https://github.com/john-ops-lab/DataLinkRuntime/releases/tag/v0.4.4), particularly AI history retirement and backup requirements. Existing automatic cache-cleanup settings remain applicable; see [cache management](../issue139-cache-governance.md).
