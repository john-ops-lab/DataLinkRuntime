# HTTP 持久接收

HTTP 来源适合由上游主动向 DLR 发送独立 JSON 数据。DLR 先保存消息及处理责任，再交给适配器代码执行。**收到 HTTP 202 表示数据已经保存，不表示业务处理成功。**

它与原 Webhook 是两种入口。原 `/api/hooks/{public_id}` 的 `accepted` / `completed`、`execution_id` 和等待结果方式保持；现有 Webhook 不自动迁移。

## 配置与开启

1. 部署管理员显式开启事件来源及 `DLR_HTTP_INGRESS_ENABLED=true`。HTTP 能力默认关闭；部署容量仍由平台配置控制。
2. 在任务适配器的运行设置中选择事件触发和 HTTP 来源，选择一个 `token` 类型的账号凭据。只保存引用，页面不展示 token 真值。
3. 保存来源后取得相对接收地址 `ingress_path`。保存、检查接收配置和保存代码都不会开始接收，也不会发送模拟业务消息。
4. 保存处理代码、选择固定运行节点后，明确开启接收。HTTP 接收同样需要有效的运行器所有权；尚未就绪时新请求返回 503。

入口位于适配器内，不增加独立事件订阅菜单。外部来源 token 只允许向本来源发送数据和查询安全状态，不能访问管理 API、重放、跳过或重置。

停止 HTTP 接收会在同一事务中使接收租约失效，故障后遗留的旧租约也能正常停用。已经接收的记录继续处理；尚未结束的请求工作仍占用原名额与内存，直到实际结束。存在未完责任时，原有的代码、凭据及来源配置编辑限制保持。

## 发送单个 JSON 值

接收接口为 `POST /api/ingress/{public_id}`，需要：

- `Authorization: Bearer <来源 token>`，使用当前有效账号凭据；管理员 token 不能替代来源 token。
- `Content-Type: application/json`，可指定 UTF-8。只接受未压缩 UTF-8 正文。
- `Idempotency-Key`：1–128 字节可打印 ASCII，由发送方为每条消息分配稳定 ID。
- 正文为一个 JSON 值，对象、数组、字符串、数值、布尔及 `null` 均可。逐条处理时，适配器从 `input.data.payload` 取得完整解析值；业务批次输入见下文。系统不自动清洗、截断或补默认业务字段。

示例中的地址和变量均为占位值。发送方需要保留原始文件，不能每次重试重新序列化：

```sh
curl --request POST "$DLR_URL$INGRESS_PATH" \
  --header "Authorization: Bearer $SOURCE_TOKEN" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: upstream-message-000001' \
  --data-binary @message.json
```

原始正文的 SHA-256 用于判断内容是否相同。因此 `{"value":1}` 和 `{"value": 1}` 是不同正文。相同 ID 改变空格、字段顺序或数字写法也可能产生冲突；不同 ID 的相同正文是不同合法消息。

## 响应与安全重试

| 响应 | 含义与发送方动作 |
| --- | --- |
| `202` | 首次消息已持久保存。保存返回的 `receipt_id` 和相对 `status_url`，继续查询业务状态。`execution_id` 暂时可以为 `null`。 |
| `200` | 同 ID、同原始正文的已保存记录读回。返回同一接收记录及当前状态，不新建初始责任或增加容量占用。 |
| `401` / `404` | 当前认证无效或入口/记录不可见；先核对来源账号和地址，不用管理员 token 代替。 |
| `409 event_identity_conflict` | ID 已对应另一份原始正文。保留首次消息，检查上游 ID 复用，不盲目换 ID 绕过冲突。其他合法 HTTP 消息不因此永久阻塞。 |
| `409 ingress_disabled` | 新接收已停止。等待明确开启；已经保存的消息仍继续处理。 |
| `410 ingress_epoch_retired` | 地址已经退役，且该旧地址没有此 ID 的已保存记录。新消息需要使用当前地址。 |
| `413` / `415` / `422` | 大小/结构超限、格式/压缩不支持或 JSON/ID 不合法。修正发送内容后再发送。 |
| `429` / `503` | 暂无容量或平台暂不可接收。遵守 `Retry-After`，使用原 ID 和原始正文有界重试。 |
| 超时或连接断开 | 不能据此认定没有提交。保留原 ID、原始正文，重试同一请求；已有 `receipt_id` 时也可查询。 |

应用的 429/503 提供 1–30 秒范围内的 `Retry-After`，当前实现为 1 秒。发送方应有持久待发送队列、有限并发、总重试期限与告警，避免无限并发和热重试。只有明确收到持久接收响应或查到原记录，才能从发送方的待确认列表移除；业务成功仍要另行判断。

查询为 `GET /api/ingress/{public_id}/receipts/{receipt_id}`，使用同一路由的当前有效 token。返回接收时间、处理状态、执行关联和安全错误码，不返回消息原文、处理代码、业务输出或凭据。`pending` 表示等待处理，`processing` 表示处理中，`succeeded` / `failed` 等为当前责任状态；接收成功与业务成功分别追踪。

## 地址、账号与处理绑定

- 地址由系统生成，固定绑定原订阅及来源 epoch，不能编辑成另一个来源的地址，也不复用已删除地址。
- 停用后，原 ID/原文仍可读回，状态仍可查询；额度已满、功能关闭或内部队列暂不可用也不取消已保存记录的读回。
- 重置来源会生成新地址。旧地址在留存窗口内仅允许读回原记录；未命中的 ID 返回 410，不能按新 epoch 再接收一次。删除订阅后旧地址返回不可见，即使永久删除适配器也保留不可复用标记。
- 当前 token 轮换后旧 token 立即失效，包括历史查询。普通来源配置和账号引用修改必须停用、确认关闭并排空；当前 HTTP 配置下更换 token 引用不强制创建新地址。
- 每条消息固定保存代码版本、运行节点和凭据引用等激活绑定。等待或自动恢复不会把旧消息悄悄换成最新代码。凭据真值不写入消息或快照。

## 资源和留存边界

单正文上限 64 KiB，完整事件上限 256 KiB；JSON 深度上限 32，总节点数上限 4,096，对象成员名也计入。重复对象成员、非标准/非有限数值及无法无损保存的字符串或数值明确拒绝。读取总时限 5 秒，空闲时限 2 秒；未知 `Content-Length` 同样受限，压缩正文不支持。

HTTP 最多 32 个在途请求，正文及事件预留合计最多 8 MiB，属于所有来源共用的 64 MiB 应用缓冲预算。HTTP 解析和数据库工作的原生并发上限为 8；HTTP 与原生事件来源共用一个最多 8 连接的 `intake` 数据库池，管理与恢复另有最多 4 连接的保留池，两池均不允许额外溢出连接。资源耗尽时拒绝，不无限排队。客户端取消后，尚未结束的原生工作继续占用其名额，直到实际结束。

每个请求按正文与完整事件上限预留 320 KiB，因此字节预算最多可同时容纳 25 个这样的预留。既有字节预算已不足时，新接收请求可在读取正文前直接收到同样的 429；查询和管理请求仍走原流程，预算不会因提前拒绝或客户端取消被提前释放。

默认原文保留 7 天、去重元数据保留 30 天；未完成、失败或仍被恢复引用的数据继续保护。发送方的约定重试期限必须位于公布的去重窗口内，窗口外不承诺永久去重。原始正文、完整事件及必要历史副本均计费，不能只按用户正文估算容量。

## 数据库存储检查

默认 Compose 将 PostgreSQL 使用的同一个 `dlr_pg_data` 卷只读挂到 Control 的 `/var/lib/dlr/ingress-storage`，`DLR_INGRESS_STORAGE_ROOT` 默认指向这里。检查只读取剩余空间，不初始化、写入或更改数据库卷权限；artifacts 卷与数据库卷的剩余空间不能互相替代。

独立运行 Control 或使用外部数据库时，管理员必须显式配置一个已存在的绝对目录，证明它代表数据库实际可用的容量域。覆盖 PostgreSQL 数据卷或数据库地址时，必须同时核对 Control 的观察挂载与此配置；只修改路径字符串不能建立容量等价。缺失、空值、相对路径、非目录或无法读取时，新接收按存储不可用拒绝；系统不创建目录，也不回退到当前目录或根文件系统。原责任排空及原记录读回保持可用。已有 `.env` 中指向 artifacts 或其他旧路径的显式值不会自动改写，升级时必须核对并更新。

默认拓扑将数据与 WAL 放在同一卷；自定义 WAL、tablespace、独立磁盘或托管数据库配额需要覆盖各个相关容量域。应用无法从任意本地目录自动证明远端数据库剩余空间；没有可证明的等价挂载或权威容量来源时，保持新接收关闭。5 GiB 停止、6 GiB 恢复的门槛不变，路径配置本身不代表容量已验收。

## 底层接收合并与业务批次

显式选择“一次处理多条”后，系统可以在底层将 HTTP 最多 4 条、RabbitMQ 最多 16 条消息合并到一次接收事务，原文加完整事件合计仍最多 1 MiB，最多额外收集等待 5 ms。这称为接收合并（MicroT1），无需另行配置；5 ms 限制额外等待，单条解码和校验耗时仍计入接收时间，截止后 RabbitMQ 只可排出 SDK 已完整收到的消息，不再做 I/O 或等待。普通逐条处理方式保持原路径。

RabbitMQ 原生 credit 上限为 16，仍使用原 2 MiB 监听缓冲及所有来源共用的 64 MiB 预算。每个新窗口在首条准备拿到工作区之前暂停后继预取，避免大消息挤满缓冲后无法前进；后续读取预算不足时，已准备的合法前缀可先提交，在接收暂停时确认，再释放预算继续读取，不标成坏消息。未能安装受检 SDK 门禁时保持单条接收。接收组实际大小由消息字节和可用预算决定，不保证每组收满，也不代表吞吐验收通过。

每条消息仍有独立身份、接收记录和处理责任。HTTP 的 202/200 只有在事务确认提交后才返回，每个请求仍独立报告错误；RabbitMQ 仅在确认提交后 ACK 已接管的连续有效前缀，提交结果不明时不 ACK。接收合并不改变安全重试、去重或逐条确认规则。

[业务批次](event-business-batch.md) 决定适配器代码如何一次处理多条输入，单次上限为 100 条、完整输入 256 KiB，并要求逐成员报告结果。底层接收合并只减少接收事务的重复开销，两种分组可以不同；接收事务提交仍不代表任何成员的业务处理成功。

## 升级与回退

迁移新增可空原文字段、不可复用 HTTP 路由和容量审计，不改写旧来源身份、内容哈希或输入。上线前备份并验证旧待处理、失败和 Kubernetes 控制责任；新入口默认关闭。

回退前先停止新接收，排空或保留可读责任，使用能理解当前来源及数据库结构的兼容版本。已经产生路由或容量审计时，迁移拒绝直接降级删除它们；不得通过清空数据或删除新责任强行回退。功能、容量和故障恢复的实际通过范围以对应测量报告为准，配置说明不代表容量已经验收。
