# 一次处理多条事件

HTTP 数据推送和 RabbitMQ 来源可以显式选择“一次处理多条（代码需支持）”。每次运行按顺序处理一组数据，每条数据保留自己的接收记录、编号和处理结果。默认仍逐条运行；Kafka、RocketMQ 和 Kubernetes 不提供此业务处理方式。

## 在适配器内设置

1. 先停止接收并处理完已有事件；尚有未完成责任时，不能更改处理方式。
2. 在“编辑”页准备能够处理多条输入的代码。展开“多条事件代码支持”，仅在代码确实支持时勾选“这段代码支持一次处理多条事件”，然后保存新版本。勾选只修改版本草稿，不修改代码、不自动保存或运行。
3. 在“运行设置 → 配置来源 → 高级设置/高级连接设置”选择“一次处理多条（代码需支持）”并保存。此时来源仍未开启。
4. 保存运行节点等设置后，明确点击“开启接收”。系统会检查已保存代码的支持声明；代码或声明不匹配时拒绝开启，原事件仍保留。

支持声明对应版本 `runtime_config` 中的 `{"event_batch_schema":"dlr.event.batch.v1"}`。已有其他运行参数保持；无效或非对象配置不会被声明控件覆盖。代码、运行参数或来源配置有未保存修改时，先按原工作台流程保存或放弃。接收/排空期间，编辑锁及原有权限仍生效。

## 代码需要处理什么

输入 `schema` 为 `dlr.event.batch.v1`；`members` 按处理顺序排列。成员包含 `receipt_id`、`delivery_id`、`delivery_ordinal`、`member_index` 和 `input`。`input` 是该条数据原来的完整事件；其中 HTTP 正文位于 `data.payload`，RabbitMQ 原文位于 `data.value`（base64）。

代码应对每条数据完成真实业务操作及幂等提交后才报告成功。遇到失败或提交结果不明就停止，不继续写入后继数据。下面展示结果结构，标识和顺序必须原样来自输入：

```python
result = {
    "schema": "dlr.event.batch.result.v1",
    "batch_id": input["batch_id"],
    "manifest_hash": input["manifest_hash"],
    "members": [
        {
            "receipt_id": member["receipt_id"],
            "delivery_id": member["delivery_id"],
            "delivery_ordinal": member["delivery_ordinal"],
            "member_index": member["member_index"],
            "status": "succeeded",
            "error_code": None,
        },
        # 按输入顺序，完整列出每个成员的真实结果。
    ],
}
```

此片段只说明格式，不能在未执行真实业务写入时照填成功。配置抽屉中的代码说明提供顺序处理骨架，其中业务函数未实现时会明确失败。参考 PostgreSQL 写入应使用稳定编号和内容核验，避免重试产生重复有效修改；任意业务代码仍需自行落实这些行为。

结果允许全部成功，或“成功前缀 → 首条失败/结果不明 → 后续尚未处理”。失败后的成员用 `not_run`、`predecessor_failed` 表示；成功成员的 `error_code` 为 `None`。不要遗漏、重复、调换标识或返回额外成员，也不要把每条业务正文塞进结果。缺失、截断或无效结果不能证明任何成员成功。

一组最多100条，完整运行输入最多256KiB，组装等待最多50ms。实际条数会受事件包装大小限制，界面不承诺每次都能凑齐100条；同一适配器仍至多一个活动执行尝试。

## 查看结果及取消影响

在适配器原“执行记录 → 接收记录”查看每条结果，并通过“本次一起处理N条”进入同一次运行。执行详情提示这次共有多少条以及取消范围。

| 页面结果 | 含义和下一步 |
| --- | --- |
| 处理成功 | 已取得可信的该条业务成功结果 |
| 处理失败 | 处理代码报告失败；检查具体原因、修复后按原编号补处理 |
| 结果未确认 | 目标可能已经写入；先核对目标，再以原编号和原文处理，不能当作从未执行 |
| 尚未处理 | 前面的数据未成功，或运行可证实尚未开始；先处理前序问题，再补处理本条 |

取消共享运行会影响其中所有尚未完成的成员，不提供“只取消这一条”的假象。Control 已确认的成功结果保持；未能确认的结果仍需核对。取消不是回滚目标数据。

首版仍逐条进行补处理、代码修复和显式跳过，并保存原失败与操作审计。单独补处理也保持该条原来的多条输入形状（单成员数组）。当前来源处理方式不同于原方式时，不能直接选择“改用当前运行配置”绕过合同；使用原运行配置，或在完整核对后另建新数据请求。

## 验证边界

此页说明操作和数据合同；代码声明、创建运行、HTTP接收成功、Broker确认及整批进程退出成功都不能代替每条业务结果。容量和恢复是否达标，以对应真实轮次、资源和逐条对账报告为准。
