# cluster-ingress-capacity Specification

## Purpose

定义双 Control 的部署级订阅额度、各节点的资源预算以及基于远程 PostgreSQL 容量观测的新接收门禁。容量 provider 的外部高可用和数据库主备切换由基础设施部署另行验证。

## Requirements

### Requirement: 新增 Control 不复制订阅与接收额度
数据库 SHALL 对整个部署统一裁决最多 16 个启用订阅、既有持久责任配额和默认每订阅 10/s、全局 50/s 速率。合法旧责任的读回或重复请求 MUST 保持已有幂等和计费规则。

#### Scenario: 启用、接收和下调竞争
- **WHEN** 两个节点同时争抢最后一个订阅或接收额度，或者管理员下调额度时已有占用超过新值
- **THEN** 数据库只允许取得剩余额度的事务成功，第 17 个启用订阅被拒绝；既有责任保留，后续新增负载按新额度背压。

### Requirement: 节点资源各自有界并为恢复保留资源
双节点首次部署 SHALL 将 HTTP 在途总数限制为 256、HTTP 子预算合计 16 MiB、来源应用缓冲合计 128 MiB、intake 数据库连接合计 16。单节点须能承担全部 16 份 owner 责任。owner 和连接诊断共享有界名额，owner 接管优先。管理及恢复须保留独立连接预算。超出登记容量或指纹不符的节点 MUST 拒绝新的 intake。

双 Control 接收模式运行期间，每个节点固定为 owner 保留全部 16 个共享原生名额，即使当前只启用 0–15 个订阅也不出借。在线原生连接诊断一律有界返回容量繁忙，名额裁决不进行数据库预查、不开 SDK 或后台线程；原有认证、权限及请求校验仍适用。单 Control 保留既有 owner/诊断共享和超时后实际关闭才释放的规则；仅在来源服务静态关闭且原入口允许时，可使用原受限的本机诊断，不另建资源池。

#### Scenario: 15 份启用订阅增至 16 份时收到原生诊断
- **WHEN** 双节点接收运行中，B 收到原生连接诊断请求，A 启用第 16 份订阅后退出
- **THEN** B 在名额裁决时直接返回容量繁忙，既未查询启用数也未启动 SDK，持续诊断压力不能占用 16 份 owner 名额。工作实际结束前继续占用原资源；单个来源的接管时限按其协议与第 14 组验证。

### Requirement: 数据库容量样本属于指定域和 epoch
远程模式 SHALL 从固定的受认证 HTTPS provider 读取有界 JSON，校验 schema_version、cluster_id、storage_domain_id、topology_epoch、observed_at 和 writable_free_bytes。观测合同要求保守覆盖可写主库及声明的可提升副本的数据和 WAL 空间。新 ID 的接受事务 MUST 在数据库权威行锁内按数据库时钟重新核实最新状态，采样和获取时间最多 15 秒，采样未来偏差最多 5 秒。单机原部署可继续观测对应本地数据卷。

#### Scenario: 低水位、过期和互相矛盾的样本
- **WHEN** B 更新容量时 A 正在等待 T1 锁，或 A 在重启后收到较旧观测
- **THEN** 两节点沿同一数据库顺序裁决；可用空间 ≤5 GiB 停新接收，停止后达到 6 GiB 才可恢复。旧值不能覆盖新值；同时间戳冲突保持拒绝，直到更新且合法的样本满足恢复条件。

#### Scenario: 观测缺失与旧责任读回
- **WHEN** 容量过期、配置不符、provider 不可达或响应无效，而数据库仍可查询既有责任
- **THEN** 新 ID 被拒绝并返回容量不可用原因，旧 ID、合法幂等重投与结算按原权限继续。Control 本地磁盘和数据库逻辑大小不能替代远程容量证据。

### Requirement: 容量配置离线切换并保留账本
管理员 SHALL 在停新接收、排空原工作、隔离旧运行角色会话后，以部署 owner 切换容量指纹与 epoch；旧样本和旧节点的 intake 权限 MUST 失效。

#### Scenario: 旧配置节点恢复
- **WHEN** 原节点在切换后重新连接，或新节点仍未得到新 epoch 的合法观测
- **THEN** 既有占用和凭据边界保留，旧节点不能启用 intake，新节点获得有效匹配观测且满足恢复阈值和集群预算后才开放新接收。

#### Scenario: 区分本节点配置错配与当前 epoch 样本不可用
- **WHEN** 离线切换后 A 的部署声明及运行配额 fingerprint 与当前数据库容量权威匹配，B 仍使用旧运行配额；新 epoch 尚无有效观测或后续观测已过期
- **THEN** 聚合健康 SHALL 分别报告 A 的 capacity_compatible 为 true、B 为 false，A 的 PostgreSQL 容量功能不可用。无法读取配置权威时不得报告匹配；新鲜匹配样本恢复只更新容量功能状态，不能把 B 的旧配置变为匹配。

### Requirement: PostgreSQL HA 切换后重新建立容量权威
声明已确认责任零丢失的部署，其外部 PostgreSQL 供方 MUST 保证每个可提升同步副本持久保存已确认提交，并独立于 DLR 裁决提升资格。切换时 MUST 关闭运行入口、隔离旧运行会话和旧主，在确认候选满足持久性要求后才可提升。新主开放运行写入前 MUST 已建立所需同步副本保障。运行入口开放期间不得取消提交的同步等待或降低所需确认数以释放等待。

#### Scenario: 切换时旧样本仍在有效期
- **WHEN** 外部供方提升候选，旧主的容量样本仍在 15 秒有效期内
- **THEN** 部署 owner SHALL 按离线流程推进 topology_epoch。新 ID 接收 MUST 保持关闭，直到固定的受认证 provider 依据新主所在时间线，重新观测新主及全部可提升副本的实际数据与 WAL 文件系统，返回与当前 cluster、domain、epoch 匹配的 v1 样本，并满足既有恢复水位及预算。

### Requirement: 模式 C 的 API 与数据库入口可独立切换
模式 C 的 HTTPS API 与 PostgreSQL SHALL 使用独立的稳定服务地址和可独立切换的代理。采用 HAProxy 与 VRRP 的部署 MUST 为两种服务分别配置代理进程、VRRP 实例和 VIP。

#### Scenario: 活动 API 代理冻结
- **WHEN** 注入前 API 与数据库健康、两台 Control 各持有效租约，客户端已建立 SQL 会话；在真实容量观测持续匹配当前权威、新鲜且足量，接收预算充足的条件下冻结活动 API 代理
- **THEN** PostgreSQL 入口 MUST 保持可用，注入前的同一 SQL 会话 MUST 无需重连即可持续查询并完成真实事务，两个原 Control 实例的租约 MUST 持续有效并续期。客户端 SHALL 在故障发生后 60 秒内经原稳定 HTTPS 服务地址，使用冻结前未用过的新 ID 完成合法请求并独立读回已接受记录，后续合法新请求也须经同一地址成功。采用 HAProxy 与 VRRP 时，还须核验原 API VIP 已由备用节点接管。
