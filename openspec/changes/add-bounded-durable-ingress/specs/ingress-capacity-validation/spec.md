# Spec Delta

## Purpose

定义 DLR 接入与处理容量结论必须具备的证据，使用户能区分小样本基线、正常突发容量、故障恢复和长期运行的实际验证范围；固定工作负载与资源边界，避免用局部成功、计数或配置声明替代完整业务结果。

## ADDED Requirements

### Requirement: 前置基线覆盖真实完整处理链路
系统的容量工作 SHALL 在新 HTTP 持久入口和完整界面实现前，使用已有 RabbitMQ 来源、普通 Python Adapter、200 条独立且各为 2,048 bytes 的 JSON、真实 Worker/沙箱及独立幂等目标形成基线。输入身份、内容哈希、预期转换结果和资源/软件清单 MUST 在运行前冻结，安装及 20 条预热与正式输入分开。

#### Scenario: 第零阶段按约定执行
- **WHEN** 后续获得实施授权并开始 B0
- **THEN** 运行前固定精确 SHA、镜像/依赖摘要、资源实际读回、目标事务/唯一键及计时参数；正式 200 条不预处理、不换成模拟 Worker 或单个大数组

#### Scenario: 环境或输入不满足
- **WHEN** 沙箱预检失败、资源/输入与约定不符，或发生器没有形成规定突发
- **THEN** 标记 NO_COUNT 并保留原因，不把该轮计为通过，也不直接判为产品容量失败

### Requirement: 容量证据受同一资源上限约束
基线与正式容量轮次 SHALL 在最多 4 vCPU/8 GiB 的单机 Linux/cgroup v2 平台上运行；接收/管理应用合计 RSS ≤1 GiB，固定 Worker 含子进程内存上限 2 GiB、两个执行槽，同 Adapter 最多一个 active Attempt，来源应用缓冲合计 ≤64 MiB。数据库、内部 Broker、代理与观测开销 MUST 计入平台预算；外部发生器/来源/目标资源及共享竞争另行固定。

#### Scenario: 拆进程或增加服务
- **WHEN** 实现将 HTTP 接收从管理进程拆出，或增加观测进程
- **THEN** 仍按接收/管理总 RSS 和平台总资源核验，不通过拆分或移出平台必要组件规避上限

#### Scenario: Worker 默认资源与基准不同
- **WHEN** 默认 Compose 资源超过基准上限
- **THEN** 使用受支持的配置满足本轮两槽及管理预留，并读回实际限制；原有隔离预检完整通过才计数，不以配置文本代替运行证据

### Requirement: 接收和处理成本必须分别测量
报告 SHALL 分别给出来源确认、连接/锁等待、接管提交、调度/派发、真实执行准备、目标写入、结果回报和后继推进的观测，以及至少每秒资源/积压采样。缺测 MUST 标为未知而非零；分位数、样本数和真实积压窗口完成速率分别报告，不能用 p50 倒数或发送速率推算处理容量。

#### Scenario: 小样本没有形成可用积压窗口
- **WHEN** 无法确认持续积压或阶段计时受时钟/观测干扰
- **THEN** 保留未知项并只补必要证据，不宣布单条模型或业务批次必然达标

#### Scenario: 带观测补丁测量
- **WHEN** 现有字段不足，需要最小观测补充
- **THEN** 单独记录实际 SHA、诊断差异和开销，不改变原锁/确认/等待行为，不把补丁运行冒充未经修改的基线

### Requirement: 第零阶段通过不等于容量通过
B0_PASS SHALL 要求约定资源/输入有效、200 条逐项对账、无重复有效业务效果或责任丢失、关键观测可用以及有依据的路线初判。B0 MUST NOT 要求旧实现已达到 16.7 条/秒，也不得替代一万条验收。安全窗口为首次发布起 900 秒；资源越界、数据异常或到期未收敛 MUST 停止新增压力并保留首败和未完责任。

#### Scenario: 200 条全部正确但吞吐低
- **WHEN** B0 完整满足正确性和测量判据，但实测完成速率低于正式目标
- **THEN** 可判 B0_PASS 并列出已证实的瓶颈；一万条容量继续显示未验证，不降低父 Issue 目标

#### Scenario: 数据错误或观测缺口
- **WHEN** 出现内容/责任不一致、OOM、并发破坏、超时未完成或无法据此判断路线
- **THEN** 标记 B0_BLOCKED，保存第一轮证据并列出具体补测/修复项，不剔除失败样本重新算成功

### Requirement: 一万条正式验收分别核对接管和业务结果
正式容量 SHALL 分别验证 HTTP 与 RabbitMQ 的 10,000 个唯一 ID、每条 2 KiB 的突发，首次到达/确认发布窗口 ≤5 秒、最后唯一持久接管距 T0 ≤60 秒、全部业务结果距最后接管 ≤600 秒。T0 MUST 为真实首次到达/发布发起；正常轮次 MUST 逐 ID/哈希/预期结果核对全部有效写入，无未完、失败、跳过或放弃责任。

#### Scenario: Broker 已收到而 DLR 尚未接管
- **WHEN** 来源 Broker 已确认一万条发布，但 DLR 接管或目标处理尚未完成
- **THEN** 分别显示 Broker、DLR 与目标进度，不把 Broker confirm 或总成功计数当成正式验收完成

#### Scenario: 首轮有拒绝而重试后完成
- **WHEN** HTTP 首轮出现 429、503、超时或结果不明，发送方保留原 ID/原文重试
- **THEN** 披露首轮成功率、结果不明、总尝试数和重试放大量；按原 T0 核对 60/600 秒，不能重置计时，首轮无需承诺 100% 成功

### Requirement: 容量验证同时保护管理面和长期责任
正式轮次 SHALL 检查已认证列表、接收记录和积压查询，无负载导致的 5xx，各接口 p95 ≤max(500 ms, 预热后空闲 p95×2)，报告采样量及超时。至少每秒采集资源/队列/速率，排空后再观察 10 分钟。SHALL 验证各层配额/磁盘低水位、重复冲突、配置绑定和大报文等定向负测，未完责任不因清理消失。

#### Scenario: 接收成功但管理操作被拖住
- **WHEN** 目标写入完成但管理接口超出约定延迟或负载引发 5xx
- **THEN** 正式容量仍不通过，报告管理资源瓶颈，不以健康接口正常替代

### Requirement: 故障恢复证据绑定准确触发点和时限
正式交付 SHALL 包含目标真实不可用 60 秒后的自动恢复，以及 T1 前后、Outbox、Claim/journal 后和目标写入后结果回报前的定向故障。目标恢复后 ≤600 秒自动完成约定轮次；其他场景恢复服务后 ≤120 秒恢复推进、≤600 秒完成对账或既有明确处置。必须保留原失败，且无重复有效业务效果、重叠 active Attempt 或重复配额释放。

#### Scenario: 下游恢复后依靠人工操作完成
- **WHEN** 目标恢复后需要人工 replay、skip、扩大额度或临时改重试策略才能完成
- **THEN** 不判自动恢复通过；保持首败和原责任，单独记录后续处置

#### Scenario: 正常容量与故障样本不同
- **WHEN** 仅故障小样本或一条链路成功
- **THEN** 不替代 HTTP/RabbitMQ 的正式一万条正常轮次，也不外推永久磁盘损坏、整机丢失或跨主机 HA

### Requirement: 业务批次以实测和逐条责任合同为前置
单条优化后的真实完成节拍 SHALL 决定是否进入业务批次专项设计。业务批次实施前 MUST 明确并审查成员绑定、输入/结果、Execution/Attempt 关系、部分成功、取消、未知结果、顺序、配额和逐项恢复；仍保留每条身份及业务效果核验。仅提升派发批量不得宣称摊薄了沙箱成本。

#### Scenario: 发布吞吐提高但业务处理仍不足
- **WHEN** Outbox 变快，实际目标完成仍未达标
- **THEN** 继续定位真实执行成本或进入专项设计，不因局部指标成功宣布父 Issue 完成，不默默开放同 Adapter 多并发
