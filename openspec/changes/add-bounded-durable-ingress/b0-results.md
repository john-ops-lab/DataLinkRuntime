# B0 Results

## Conclusion

**测量判定：B0_PASS。** 2026-10-26 已完成隔离平台上的 20 条预热和一轮正式 200 条真实 RabbitMQ → 持久接管 → 固定 Worker/真实沙箱 → 独立 PostgreSQL 目标链路。正确性、责任交接、资源和瓶颈判断均有逐条证据；一万条容量及新 HTTP 来源尚未验证或实现。

产品源码基线：`1158e413e55d92127d615d666c5d4e4bcc15514f`。正式夹具/隔离诊断候选：`e0622677934f74999d918a8ff4df69b16656ff38`；Control/Worker 镜像的 222 个 Python 源文件与产品基线逐文件一致。产品接收限速、事务、确认、前序、固定等待和沙箱语义保持原样，B1–B5 未开始。

宿主子 Agent 已独立复核原始证据及算式。Kimi OCR 已完成全部 8 个测量工具文件，未发现实质问题；早期设计文档分组因接口超时返回 partial，该回执未作为全审通过。后续文档补审的完整范围、精确 SHA 和终态单独保留于私有验收账本，不能用早期回执替代。

## Frozen Environment and Workload

- 平台独立 Linux/cgroup v2 VM，4 vCPU、8 GiB、SSD、无 guest swap；平台数据库、内部 RabbitMQ、Control、Worker、Web 和观测开销均在同一平台预算。
- 一个 Python Adapter、一个固定 Worker、两个执行槽；每 Adapter 一个 active Attempt。Worker 限额 2.5 CPU、2 GiB、512 PID；单次沙箱 1 CPU、512 MiB、128 PID、256 MiB tmpfs。原隔离预检通过，全部公布的隔离能力为 true。
- 外部来源、独立目标库和发生器使用独立容器/卷/网络与合计 2 CPU、4 GiB 的资源组，位于平台 VM 外；与另一 VM 的原有工作负载共享宿主资源。这是该测试台的基线，不外推裸机或其他部署。
- 正式 200 个唯一 ID，每条原文精确 2,048 bytes；预热 20 条使用独立 ID。每条轻量转换后独立连接、独立同步提交目标事务；未合并业务、未跨 Attempt 复用连接、未加下游自动重试。
- RabbitMQ 4.3.5 使用仓库固定 digest；Python 3.13.16、Pika 1.3.2、psycopg 3.3.4。平台与目标使用同一 PostgreSQL 16 实际镜像。psycopg 两个原始 wheel 的 SHA-256 与锁文件一致，安装内容逐文件核对 120 个文件无差异。
- 单订阅默认 10/s、pending 1,000/32 MiB、history 10,000/256 MiB；全局及 Admission/Outbox/tick 使用原默认值。未提高配额、删除历史、跳过责任或绕过沙箱。

## Timing Basis

**分段性能使用同一平台 VM 的 monotonic；结束点为 `start_ns + elapsed_ns`，不是日志写入时间。** 原始 UTC 与 monotonic 的关系在采样全窗变化约 8.119 秒，外部时钟偏差超过 5 ms；517 个时钟探针有效，6 个不可用但保留了对应资源样本。未确认漂移根因。

- 来源发生器自身 monotonic：首次发布至全部 Broker confirms **约 21 ms**。
- 首个至最后一个 T1 commit：**38.651 秒**。
- 首次 T1 custody 开始至最后 Delivery 终态 commit：**407.268 秒**；控制器另一个时钟域观察约 403 秒，两者不混算。
- 最后 T1 commit 至最后 Delivery 终态 commit：**368.591 秒**；该窗实际结清 179 个责任，**0.486 条/秒**。同窗实际完成 178 个目标结果，约 0.484 条/秒，相差一条由目标已提交但平台尚未结清解释。
- 跨 VM 的精确 `T_accept−T0` **未测得**。没有用未校正 UTC 差伪造精确接管时延；本轮能支持完整链路与瓶颈判断，正式一万条验收前须修复/约束计时环境。

未用 p50 倒数推算容量；0.486 条/秒是持续积压窗口内的实际完成计数除以实际时长。

## Measured Bottlenecks

下表是正式 200 条的同 VM 计时摘要；分位数使用 nearest-rank。完整 49 项的样本数、均值、P50/P95/P99、最大值和负值计数见 [完整阶段统计](b0-stage-statistics.md)。包含关系的阶段不能相加。

| T1 commit | 200 | 0.754 ms | 1.742 ms |
| T2 物化函数体 | 200 | 26.754 ms | 45.093 ms |
| T2 commit 至发布开始 | 200 | **468.229 ms** | **986.321 ms** |
| 实际发布路径，含 channel/confirm/close | 200 | 5.804 ms | 12.082 ms |

| 其中 psycopg 导入 | 200 | 119.500 ms | 171.940 ms |
| 目标连接 | 200 | 15.921 ms | 31.366 ms |
| 目标 commit 返回 | 200 | **1.420 ms** | 3.158 ms |
| 结果 commit 至 Delivery 终态 commit | 200 | **1,111.839 ms** | **2,331.376 ms** |

199 个相邻责任完成周期总计 405.853 秒，可无重叠分解为：前序结清到后继 T2 commit 1.53%，T2 commit 到 Claim RPC 开始 23.37%，Claim 到结果 commit 20.34%，结果 commit 到 Delivery 结清 54.75%。**派发与完成确认前的等待合计约 78.12%。** 不是把包含彼此的执行/handle/导入成本重复相加。

完成确认等待与共享 100 条分页有明确相关证据：前 100 条平均 1,633 ms、后 100 条 590 ms；全部接管后按精确瞬时未结清数分类，超过 100 时的 78 条平均 1,845 ms，不超过 100 时的 100 条平均 590 ms。后半段 Worker 执行反而更慢，不能将处理节拍加快归因于业务代码变快。结合 pending/processing 共用分页及固定 tick 的源码，这是优先调查方向；本轮未做移除分页的因果对照。

诊断全窗 `dispatch_delivery` 调用 17,875 次，仅 200 次物化，98.88% 未物化。保守选择正式活跃窗内 13 个完整聚合批次，记录 228,279 次 SQL，其中三个扫描/上下文/锁父阶段占 71.72%。SQL P95 在 (0.5, 1] ms、P99 在 (1, 2] ms；连接池 checkout 均值约 0.013 ms，P95 ≤0.1 ms。**首要问题是重复工作与等待，不是已证实的连接池容量不足。** SQL 包含查询执行与锁等待组合，未声称测得纯锁等待。
