## 目标连续不可用 60 秒，一千条自动恢复

候选为 `0f8cf7a28ce7332aca87695a4e8a1548e91090c4`。使用独立 RabbitMQ 来源、1,000 条各 2,048 bytes 的固定原文、普通 Python 业务批次参考适配器及独立 PostgreSQL 目标；资源与正式容量配置保持原约定，不修改正在使用的主目录或原开发环境。

- 发生器只发布一次，保留同一运行编号、消息编号及原文；目标在发布前已真实关闭，保持关闭至少 **60.000263 秒**，随后启动同一目标容器和持久卷。
- 参考适配器日志保留 **11 次真实 `OperationalError` 连接失败**及后续重试成功，日志未截断；最终有 17 个成功 Execution。不是通过手工修改状态模拟故障。
- 目标及平台两个独立 oracle 均按原 1,000 条完整核对。目标逐条编号、业务哈希、转换值及有效写入恰为一次；平台核对原文、Envelope、批次成员、冻结版本、执行、确认与记账，未完成占用、准入及活跃责任归零，Broker 排空。
- 从目标实际恢复可连接，到完成两个 oracle 和 Broker 零积压读回后再取的保守上界为 **25.192795 秒**，满足恢复后 600 秒要求。来源通过正常配置版本检查停用并确认关闭；没有人工 replay、skip、reset、调额、补发或更换身份。

目标控制器与发生器位于同一夹具 Linux 内核，已核对 boot ID 与两边 `CLOCK_MONOTONIC` 的命名空间偏移均为零；命名空间 inode 不同仍保留记录。偏移相对于初始命名空间定义，依据 Linux `time_namespaces(7)`。没有把控制/Worker 虚拟机的时间与夹具时间直接相减，也没有依赖 UTC 差判定时限。

首次预检轮次因为把命名空间 inode 必须相同作为条件，在发生器启动前停止；该轮接收数量为零，不计业务恢复通过。目标已自动恢复，来源和本轮拥有的探针已关闭，首败材料保留。修正只放行同一内核且经过验证的零偏移时钟，新轮使用新编号，没有覆盖失败证据。
