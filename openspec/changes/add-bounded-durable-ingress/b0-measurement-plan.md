# B0 Measurement Plan

## Status and Scope

**B0 已获用户授权，正在执行；后续批次尚未开始。** 设计基线是 `1158e413e55d92127d615d666c5d4e4bcc15514f`。运行前登记实际候选完整 SHA、隔离诊断包装及夹具摘要；若主线相关代码已变，重新核对差异再开始，不复用旧基线名称。测量结果另列证据，不提前填写通过状态。

B0 只回答：200 条真实消息从来源到目标的成本在哪里、哪些等待可消除、是否有必要继续评估业务批次。B0 不要求未经优化的旧实现达到 16.7 条/秒，也不证明一万条容量、所有来源、所有语言、HA 或故障自动恢复已通过。

固定链路：专用外部 RabbitMQ 队列 → 已有事件接收 → Receipt/Delivery → Execution/Outbox → 内部 RabbitMQ → 固定 Worker 的真实沙箱 → 独立 PostgreSQL 目标。使用一个 Task/manual Python Adapter 和一条 RabbitMQ 订阅。测量期间不承载其他业务适配器。

## Frozen Workload

| 项目 | 固定规则 |
| --- | --- |
| 正式样本 | 200 条独立 JSON，每条原始 UTF-8 正文恰为 2,048 bytes；不合成大数组请求 |
| 身份 | 每轮唯一 `run_id`；`message_id` 为该轮 000001–000200，既放入 RabbitMQ message_id，也放入正文；所有重投沿用原值 |
| 数据 | 顶层对象含 run_id、message_id、seq、value 和 ASCII padding；value=seq；独立生成器逐条保存原文 SHA-256 与预期结果 |
| 业务 | 普通 Python `handle` 从事件正文取值，计算 `normalized_value=2*value+1`，每条独立提交到目标；不 sleep、不预先转换正式样本 |
| 依赖 | Python 3.13，Adapter 显式固定 `psycopg[binary]==3.3.4`；安装/预热先完成；解释器、wheel、平台锁文件及镜像摘要均入运行清单 |
| 目标写入 | 每次实际执行创建一个连接、一次业务事务；不跨 Attempt 复用连接，不批量合并事务；连接/语句超时各 5 秒，Execution 超时 300 秒 |
| 幂等 | 目标主键 `(run_id,message_id)`；同键同输入哈希/预期值只读回原结果，同键不同内容明确冲突；另记有界尝试元数据，不把“仅有一行”冒称没有重试 |
| 来源队列 | 专用、持久化、单消费者；消息 persistent、publisher confirms、mandatory；无 TTL/自动删除，溢出拒绝发布，队列上限 1,000 条/16 MiB；来源 ACK 沿已有 T1 后确认合同 |
| 发布 | 单连接、单 channel，最多 32 条未确认发布；200 条在 ≤5 秒内完成向来源 Broker 的发布及确认；发布失败不得隐藏，发送方保留原文和 ID |
| 预热 | 20 条独立 warmup 消息，使用不同 run_id，message_id 为 w000001–w000020（正文与 AMQP 一致），与正式 000001–000200 不相交；等全部终态后开始正式轮次；保留预热记录，不能把正式工作隐藏在预热中 |
| 次数 | 默认一轮正式 200 条。仅因具体观测缺口、失败或后续实际优化才补测；新的轮次保留旧结果，不覆盖首败。正式消息 ID 固定，补测须在旧责任结清后显式建立新来源 epoch/隔离订阅，不能只换 run_id 向原 epoch 重发不同正文 |
| 故障 | B0 不注入停机、下游故障或数据破坏；实际发生则记录完整现象，不把失败样本剔除后算成功 |

目标库与 DLR 权威库使用不同实例、卷和凭据。参考 Adapter 只能访问目标库，不读写 DLR 内部状态。目标同步提交保持开启，独立核验程序从输入清单计算期望值，再查询目标，不能复用 Adapter 的转换函数作为唯一判据。

## Resource Envelope

以下上限适用于 B0，后续正式容量轮次沿用。实际机器、体系结构、Linux 内核、Docker/Compose、镜像 digest、存储介质与网络拓扑在执行前的私有运行清单中固定；这是环境身份登记，不允许借此放宽数值或改变工作负载。

| 资源 | 固定限制及取证 |
| --- | --- |
| 平台总量 | 一台独立 Linux 主机/VM，最多 4 vCPU、8 GiB，cgroup v2、本地 SSD；全部 DLR 服务及其子进程、数据库、内部 Broker、代理和观测开销计入；禁用 swap |
| 应用预算 | 接收/管理应用进程合计 RSS 峰值 ≤1 GiB；应用父组设置相应有限内存，后续拆接收进程仍按总和统计；代理等其他平台进程仍计入总预算 |
| Worker | 一个固定 Worker，2 个执行槽；容器 CPU 上限 2.5、内存上限 2 GiB、PID 上限 512；原有 private cgroup namespace 和 exact delegated subtree 门禁必须通过 |
| 单次沙箱 | CPU 1.0、内存 512 MiB、PID 128、tmpfs 256 MiB；保持原有有限输出/日志上限；同 Adapter 最多一个 active Attempt |
| 沙箱预算核对 | 两槽需至少 2.25 CPU、1,088 MiB memory、288 PID、544 MiB tmp 预算，仍以原预检实际读取结果为准；tmpfs 计入内存，不能额外当作免费空间 |
| 持久存储 | 开始前至少 10 GiB 可用；记录数据库/索引/WAL、内部 Broker、日志和已有占用；可用空间降至 5 GiB 停止新增发布与接管，保留已接管责任 |
| 应用缓冲 | 现有来源全局缓冲上限 64 MiB；读回生效值，并分别观察 SDK/解析分配和实际 RSS，账本值不能代替内存测量 |
| 外部夹具 | 负载发生器、来源 Broker、目标数据库位于平台预算外的独立环境，总上限 2 vCPU/4 GiB；目标内存 ≤2 GiB、来源 Broker ≤1 GiB、发生器 ≤512 MiB；记录与平台的 CPU/磁盘/网络共享关系 |
| 软件 | 来源及内部 RabbitMQ 复用基线锁定的 4.3.5 镜像摘要；目标 PostgreSQL 16 与基线 PostgreSQL 使用同一实际 patch/digest；不能只记录可变 tag |
| 网络 | 固定连接路径与 TLS 设置；记录空载 RTT、时钟误差及测试期间外部资源饱和。正式轮次保持相同网络和目标写入策略 |

Worker 默认 Compose 内存为 2.5 GiB、默认单次 tmpfs 为 1 GiB，不能直接冒充本合同的 2 GiB。B0 使用受支持的部署参数把 Worker 总内存设为 2 GiB、单次 tmpfs 设为 256 MiB，实际预检失败则本轮不计数；不降低预检要求、不删除第二槽、不绕过沙箱。其余性能相关默认值保持如下：

| 项目 | B0 固定值 |
| --- | --- |
| 单订阅接收 | pending 1,000 条/32 MiB，history 10,000 条/256 MiB，dedupe 500,000，rate 10/s |
| 全局接收 | pending 10,000 条/256 MiB，history 100,000 条/1 GiB，dedupe 500,000，rate 50/s |
| 执行准入 | 单 Adapter 100 个未完成执行，全局 1,000 个；原字节额度保持基线 |
| 调度 | Outbox 发布并发窗口 4、原每轮 1 秒等待；事件维护 tick 1 秒；原页大小/前序屏障保留 |
| 开关 | 在隔离基准实例显式开启已有事件来源；不启用新 HTTP 功能，不运行 AI、其他来源或并行背景任务 |

若无法提供上述隔离环境，结论为 `NO_COUNT` 并说明不满足项，不停止其他工作负载腾出资源，也不把共享开发环境的结果包装为正式基准。专用基准实例用于测量，不替代现有本地开发测试入口。

## Measurements and Timing

正式轮次保存以下事件与身份关联，至少包含 message_id、Receipt、Delivery、Execution、Attempt、dispatch generation。无对应阶段时明确标记“不适用”；缺测写“未测得”，不得填 0。

| 段 | 观测边界与用途 |
| --- | --- |
| 来源 | 第一次发布开始、每条 Broker confirm、DLR 实际拉取及 source ACK；Broker 收到与 DLR 接管分开画曲线 |
| 接管事务 | 连接池申请/获得、事务开始、订阅及全局配额锁请求/获得、T1 commit 返回；区分锁等待、持锁及提交耗时 |
| 接管后等待 | T1 成功至满足顺序/容量条件、至 T2 开始/提交；前序屏障等待和扫描回访等待分别标记 |
| 发布 | Outbox 创建、租约获得、连接/channel 准备、publish/confirm、持久结算；确认丢失保留不明状态 |
| Worker | dispatch 收到、Claim 请求/持久返回、journal 与 ACK、工作区准备、沙箱准备/进程启动、handle 开始 |
| 业务与结算 | 目标连接、事务提交返回、结果回报/持久终态、清理结束、Delivery 终态确认、后继获得执行机会 |
| 工作集 | 每轮扫描数、就绪候选数、实际派发数、processing 回访延迟、共享锁/连接等待、各队列积压和最老年龄 |
| 资源 | 每秒 CPU、RSS、cgroup memory.current/peak/events、PID、IO、磁盘余量、数据库连接/锁等待、Broker 深度；记录原生/解析缓冲实测边界 |

短耗时用同进程 monotonic 计时；跨进程使用有来源标识的 UTC 时间并记录同步误差。跨主机最大实测偏差应 ≤5 ms；超出时不得用未校正的跨主机差值比较 60 ms 级阶段，必须保留误差或补充同源计时。`commit 返回` 是客户端观测到的提交完成，不声称为精确 WAL 落盘时刻。

报告均值、p50/p95/p99、样本数及最大值；吞吐按持续积压窗口内真实目标提交/终态完成计数除以实际窗口长度计算，附完成间隔序列。至少有连续 30 秒可证明的未完成积压才对“积压下持续推进”作判断；不足则保留该项未知，不从发送节拍或分位数倒数推算容量。可重叠阶段不能简单相加为串行成本。

现有字段不足时，B0 可增加最小观测挂钩或隔离诊断包装，仅输出有界时长/计数/内部关联 ID，不改变锁序、提交、确认、等待或代码执行行为。记录诊断补丁及实际运行 SHA，不能把带观测补丁的运行称为原 main 原样运行。观测写入总限额 32 MiB：Control/Worker 各 12 MiB、资源采样 6 MiB、账本采样 1 MiB、预热/正式发布明细各 512 KiB。写入前按真实样本尺寸预检窗口余量，保留超限标记与进程退出状态；不输出原文、SQL 参数、凭据或业务敏感内容，材料放在仓库外。

在预热中核对观测是否明显改变完成节拍或造成资源竞争，报告开销与测量误差。无法排除观测干扰时，诊断数据只用于定位，补充同负载的必要对照后才能作路线判断；不得直接删除最慢阶段的观测美化结果。

## Execution Sequence

1. 登记 run manifest：精确 SHA/诊断补丁、全部资源限制读回、软件 digest、输入与 Adapter 哈希、配置指纹、网络/时钟、目标 DDL/唯一键/事务策略、运行身份与私有证据位置。未填完不开始。
2. 检查沙箱、固定 Worker、专用来源/目标、空闲状态和磁盘空间；仅创建本轮隔离资产，不改既有开发配置、卷、Token 或 Master Key。
3. 完成依赖安装和 20 条预热；等待全部结算，记录计数基线。正常正式消息的处理路径不得被预热跳过。
4. 启动有界采样，发布 200 条，保留发送与 Broker 确认事实。保留默认接收限速、Outbox 节奏和前序约束。
5. 等待逐条完成并对账；总观测窗口上限为首次发布起 900 秒。到期或停止条件触发后停止新发布/接收，保存尚未完成责任，进行最小定位。
6. 对照输入清单、来源、DLR 持久状态和独立目标四方数据；核对重复有效写入、ID/内容差异、并发 Slot 和占用账本；输出每段耗时及积压曲线。
7. 完成报告和静态/定向检查，审查实际差异与证据；只有结论需要的具体缺口才追加轮次。确认无未完责任后按本轮资产清单清理临时夹具，保留必要证据；不清理其他历史环境。

## Acceptance and Stop Rules

| 结论 | 判据 |
| --- | --- |
| `B0_PASS` | 资源与配置符合、200 条身份/原文哈希/目标值全部对账、有效写入各一次、来源与平台计数可解释、无超限或并发破坏、关键段观测可用，报告给出有证据的瓶颈和后续方向 |
| `B0_BLOCKED` | 数据/责任不一致、超时未排空、OOM/资源越界，或关键观测不足以定位；保留事实并列出最小补测/修复项，不宣称测量通过 |
| `NO_COUNT` | 环境/输入/固定参数不符、沙箱预检失败、发布夹具未形成规定突发、时钟/观测问题使关键证据无效；这不是产品容量失败，原因须单独记录 |

出现有效数据缺失/内容改变、重复业务效果、单 Adapter 重叠 active Attempt、OOM、资源上限突破或磁盘 ≤5 GiB，立即停止新增压力并保留已有责任。900 秒是本轮安全结束界限，不是产品性能承诺；只要完整链路符合以上判据，低于 16.7 条/秒本身不使 B0 失败。

B0 报告必须选择并解释一个结论：优先消除已测得的单条路径开销；已有证据需要进一步评估业务批次；或观测不足暂不能决定。若 200 条较快排空而没有连续 30 秒积压，但完整分段和正确性证据足以支持初步方向，可以通过 B0，并将积压下持续速率保留为未知；不为凑窗口主动延迟处理，也不因此直接扩大压测。若该缺项使路线无法判断，则为 B0_BLOCKED。**仅凭 B0 不直接批准业务批次实现**，也不修改父 Issue 的一万条目标。
