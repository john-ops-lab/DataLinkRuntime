### 持续进流下的公平扫描

首轮真实预热发现：四个 partition 的第一项 Execution 已成功，但 Receipt 投影保持 processing，后续 pending 随持续新消息增长；停止生产后才排空。原因是无上界的移动游标不断追逐新 ID，未回头观察旧责任。

候选为每轮扫描固定有限上界，再按最多 100 项分页；完成该范围后重新开始。Delivery 终态观察/派发、历史 GC、配额审计和来源候选扫描都保留游标及上界。独立真实 PostgreSQL 测试覆盖持续插入、旧上界删除和多页历史清理。修复后的 60 秒预热完成 60/60 条目标唯一写入，pending 至多 1，随后停止并排空；这只是预热结果，不替代 30 分钟容量门槛。

该缺陷与 B2 曾记录的 **125.897 秒 Control 重试调度额外延迟**不能混为同一已证原因。后者仍按 [B2 记录](b2-review.md) 保留，正常容量未复现也不能直接宣称已经修复。

### 诊断与显式处置

- 管理员读取当前 Control 实际进程的 owner 数、应用缓冲用量/峰值/上限；它不是原生客户端 RSS。
- checkpoint 只读查询当前 epoch，提供安全/已确认位置、失败屏障和有界未接管故障。`source_lag=null` 明确表示未知，不把两个位置之差当 broker lag。
- Activation 与凭据使用位置只返回版本、Worker 和引用，不解密 Secret。Delivery 记录实际激活及受限修复 Revision，保留原激活事实。
- `skip-unaccepted` 只接受当前 epoch 的匹配故障和审计参数，安全下一位置由服务端推导。原生源恢复先确认持久安全位置，再继续接收。

真实 Kafka 末条毒消息实验只生产一条 524,289 字节记录，无后续正常记录。超限后未创建 Receipt/Execution；同一显式 skip 请求重试返回同一处置，DB safe/confirmed 与真实 broker commit 均从 0 推进至 1，故障清空，监听实际关闭。探针首轮误把 JSON 字符串 offset 当整数比较，延续探针纠正了类型断言；清理阶段误用 SDK 方法名也单独纠正。这两项保留为 harness 首败，未改写为产品首轮通过。

### 当前配置补处理

只读 `replay-context` 比较原/当前 Revision、固定 Worker、配置版本/epoch、源凭据及 Adapter 绑定引用。当前配置补处理须携带同一预览指纹，服务端在 Adapter 锁内重算；变更后返回 409，不按未展示的新引用创建激活或 Delivery。结果不明时重复原请求先解析已存处置，即使后来 Adapter 合法改版，也返回同一 Delivery。请求 ID 改指纹返回冲突。指纹不代替权限，也不包含凭据真值。

排空后 Control 数据库实际增加 26,656,768 字节，约 14.81 kB/事件（含索引和 Execution 快照）；独立目标库约 3.16 kB/事件。按本次单事件增量线性推算，假设持续 1 条/秒且不受配额/回收约束，Control 约每天 1.28 GB、七天 8.96 GB、三十天 38.39 GB。这是解释增长的假设投影，**不是该配置已达的吞吐、留存后的稳态占用或存储硬上限**：默认历史 10,000 条在 1 条/秒下约 2 小时 46 分 40 秒就会触限，完整七天窗口下约只能容纳 0.992 条/分钟，补处理还会额外消耗历史预算。

基线扣除后的 WAL 生成量约 50.27 kB/事件，是写入流量而非保留磁盘；Control 平台日志约 1.03 kB/事件，包含可变的并行只读 UI 观测开销，不能纯归因于每条消息。WAL、日志与业务历史有各自的回收规则，不能把这些线性投影简单相加当磁盘采购量。后处理 helper 曾误用 oracle 参数及 JSON 结果形状，保留两次首败后只读修正对账；不重新生产或重写已存业务结果。

只读定位样本中，30 次成功 Execution 的启动间隔中位数为 1.043 秒，published→claim 中位数 3.089 秒，而 claim→终态中位数为 0.175 秒；最后一个指标包含准备与运行，不能叫纯业务函数耗时。同 Adapter 的 active Attempt 限制仍为 1，第二个 Worker 槽过早认领时会收到 DEFER 并通过 nack 返回队列。该解释符合额外 claim 请求和既有最小重投间隔，但未逐条留存 decision，不把全部差额都判定为 DEFER。

[RabbitMQ 4.3 官方合同](https://www.rabbitmq.com/docs/4.3/quorum-queues#delayed-retry)允许配置毫秒级最小延迟；nack 通常不增加失败计数，不能把它解释为指数退避。独立核对还发现，实际 broker 合并 `delayed-retry-min` 时保留较大的下限；单加较小策略不能假设覆盖现有 queue argument。DLR 的精确拓扑检查同样拒绝只改环境变量绕过原参数。首轮已完成并排空，随后完成开发队列的静默维护，实际最小重投间隔由 1,000 ms 改为 100 ms；使用既有 `DLR_RABBITMQ_RETRY_BASE_SECONDS=0.1`，Worker 两槽配置保持不变，不更改产品默认值。修订配置另做完整稳态实测，不将此改动当成 B2 重试调度延迟的已证原因。

维护保留两项实际首败：应用停止后 Management 的 consumer 统计未立即刷新，第一次门禁因此拒绝继续；刷新后所有计数为零，但 quorum queue 的条件删除返回 `not_implemented`。精确 [RabbitMQ 4.3.5 官方实现](https://github.com/rabbitmq/rabbitmq-server/blob/v4.3.5/deps/rabbit/src/rabbit_quorum_queue.erl)对 `if-unused` 和 `if-empty` 均不支持，因此最终操作没有服务端原子空队列保护。实际采用独占静默窗口：Control/Worker 停止、两次间隔超过五秒的原生 AMQP connection/consumer 列表均为空、消息总数/ready/unacknowledged/delayed/dlx 均为整数零、固定队列元数据与责任摘要匹配，并再次确认开发库备份可读后，只重建该 Worker 执行队列。正常 bootstrap 后仅最小重投参数变化；历史 DLQ、原库 135 条终态及开发库责任/Outbox 摘要、六个既有卷和凭据哈希核对保持，未操作业务数据卷。该证据是摘要和映射核对，不是两库全部行内容的哈希证明。独立审查通过；后续容量固定新配置，不热修改。

首轮正式实验中曾并行执行只读浏览器检查，详情页约每 5 秒发出 7 次只读 API 请求，随后切离详情页；采样和日志增长包含这段观测开销，不能描述成全程空闲环境。第二轮未保留该浏览器负载，比较结果不能全部归因于单一参数。

### 有限突发、三类背压和恢复

另建三个独立测试订阅，按合计 10 条/秒节拍有限发送 100 条，另有三条先行头项。每个 topic 配置四个 partition，本轮输入固定在 partition 0，验证同 partition 的失败与背压，不冒称多分区压力覆盖。数量与字节用例分别让自己的第一条目标写入返回故障；历史用例的目标正常。均保持上述固定候选和运行参数。

实际触限后连续观察 **600.244 秒、61 次物理采样**，三者的安全/确认位置及目标效果均保持。详情（三个订阅合并）1,797 次、runtime 与 health 各 599 次请求全部为 200；p95 相对各自无监听基线为 0.891、1.028、0.999 倍，无资源 5xx。独立审查已从原始样本重算资源、缓冲和完整位置，不以 HTTP 200 替代业务结论。

观察窗口的应用 ledger 当下占用保持 0，进程生命周期峰值 7,001 字节，低于 64 MiB；原生客户端额外内存仍须看进程采样。Control RSS 从 183,554,048 至 183,975,936 字节小幅正增长，Worker RSS 保持 92,078,080 字节；Control FD 首尾均 47、线程 27 至 26，没有随已暂停输入继续累积责任的耗尽。此处不宣称原生 RSS 硬上界或任意时长无增长。

短突发阶段另保留一项瞬态：仅 10 个 runtime-status 请求样本的 p95 为 23.595 ms，相对同一基线 2.604 倍；该阶段其他观测路由未超过两倍且无错误。规定的触限后完整十分钟窗口满足两倍门槛，但不能扩写为所有阶段每条路由均满足两倍。未为美化该短窗口重跑或丢弃样本。

103 个源 ID 最终分类为 **71 成功、2 显式未处理跳过、30 未接管**；共 73 份 Receipt。成功集合的完整 payload、来源身份/位置、目标一次有效写入和最终责任逐条对账通过，不能把两次 skip 算成成功。恢复未修改配额、提前清理七天原文或重放一个新的假成功来源。历史限制仍为 4，待合法治理窗口；已接管责任排空不代表剩余历史已经处理。Kubernetes 控制预留仍属 B4/B5，不能由这次 Kafka 实验代验。
