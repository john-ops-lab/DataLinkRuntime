# B0：Control 监听预算与容量基线

结论：**有界阻塞监听模型的最小隔离探针通过，可以作为 B1 实现约束；尚未证明 DLR、Kafka 或 Kubernetes 的实际吞吐/原生缓冲上界。** D7 的初始默认值保持不放宽；配额决定低频适用范围，不能把接管速率上限称为稳态能力。

## 复跑与范围

探针：[tools/subscriptions/budget_probe.py](../../../../tools/subscriptions/budget_probe.py)。从仓库根使用已安装开发依赖的 Python 3.13 环境运行：

```sh
backend/.venv/bin/python tools/subscriptions/budget_probe.py
```

可用 `--output` 把 JSON 证据写入私有目录。探针使用临时本地端口，退出后关闭所有测试监听和连接，不连接 DLR、Kafka、Kubernetes 或 PostgreSQL，不改容器、产品数据库、Worker Slot。HTTP 请求实际经过 TCP/FastAPI/Uvicorn；服务端和 HTTPX 客户端共享一个事件循环，因此这是一项隔离调度可行性基线，不是产品 API 压测。

测量环境：2026-10-23，Python 3.13.14、arm64、10 个逻辑 CPU；FastAPI 0.141.1、Uvicorn 0.52.1、HTTPX 0.28.1。数值来自该日最终探针运行，私有证据文件名为 `b0-budget-final.json`；公开记录不包含机器名、来源地址或凭据。

## 执行池与租约约束

- 使用独立 `ThreadPoolExecutor(max_workers=16)`；提交前以 16 个 permit 限额，超额立即拒绝，不能依赖 executor 自身的无界等待队列。实际客户端内部线程另计，必须单独配置并在 B2/B4 观测。
- API 循环只调度线程结果和短事务；不能在循环中执行客户端阻塞调用，也不通过 `asyncio.to_thread` 占用默认执行池。每条订阅至多一项在途客户端调用，不能持续提交排队。
- permit 与应用缓冲预留只在**原生调用真正结束**后释放，不能在 asyncio wrapper 被取消时提前释放。`Future.cancel()` 对已经运行的线程返回 false；停用/租约失效不能被解释为物理终止网络 RPC。
- 每个网络连接/读取/关闭接口必须有有限超时，停止标记由调用返回后观察。探针用 3 秒读取超时；真实 Kafka poll/commit/close 与 Kubernetes connect/read/watch 超时须按客户端能力分别限制，关闭不能无限等待。若客户端不能提供有界回收，不得以“线程 future 已取消”通过门槛。
- 初始租约仍是数据库时间的 30 秒、10 秒续租。探针的单次读取为 3 秒；真实客户端按 [b0-clients.md](b0-clients.md) 分别固定 poll、请求和关闭预算，不能把 3 秒探针扩写为全部来源接口的统一时限。续租使用独立 asyncio 管理任务和短数据库操作，不与来源长读串行。网络超时不提供数据库写 fence；T1/checkpoint 仍校验 owner、generation、有效租约，Kafka 另校验 assignment generation。B1 的竞争/数据库停顿用例才证明这部分产品行为。
- 总应用缓冲上限 64 MiB；不能把每监听器各 64 MiB 当成同一限制。最终 Envelope、批次项数、全局预留逐项校验。客户端原生缓存与 API/ORM/Execution 自身内存额外计入 RSS，不能用逻辑缓冲计数替代进程测量。

## 最小探针结果

两个 HTTP 样本各 300 次请求、并发 4、预热 30 次；阻塞阶段始终有 16 个真实 socket `recv` 在专用线程中等待。应用缓冲为总计 64 MiB 的已触页分配。

| 观察项 | 最终测量/结论 |
| --- | --- |
| 无监听 HTTP p95 | 9.33 ms |
| 16 个阻塞监听 HTTP p95 | 6.64 ms，基线的 0.71 倍；全部 HTTP 200 |
| 默认执行池 | 监听未启动默认池线程；独立 sentinel 在 0.61 ms 返回 |
| 专用线程/连接峰值 | 各 16；第 17 项立即拒绝，不进入等待队列 |
| 应用缓冲 | 峰值 64 MiB；超额预留拒绝；结束后计数为零 |
| 对运行中 native future 取消 | 返回 false，未杀死阻塞调用 |
| 原生调用/停用收敛 | 最长 3.01 秒；发 stop 后所有连接关闭耗时 2.68 秒，不超过网络超时预算 |
| 回收 | 五轮重用后关闭专用池，专用线程数 0、客户端连接 0 |
| RSS | 无监听约 54.13 MiB；阻塞时约 119.30 MiB；五轮结束约 91.83–91.95 MiB；关闭专用池后约 97.58 MiB |

全部 13 项断言通过。RSS 不要求立即回到初始值，解释器/分配器可保留已释放页；五轮短样本也不足以证明十分钟或长期无增长。更低的阻塞阶段 p95 不能解释为监听提高性能，可能来自预热与调度噪声。真正合并门槛仍是实现后的 API p95 ≤ 同场无监听基线两倍且无资源耗尽 5xx。

## 4 KiB 最终 Envelope 的逻辑估算

以下以最终序列化 Envelope 恰为 4 KiB 估算，不是原始 Kafka value；base64、字段与原内容必须已经包含在这 4 KiB 中。只计算一份 Envelope 的下界，不含 PostgreSQL 行/索引/TOAST/WAL、重复 Execution/Outbox 输入、审计、日志、客户端内存。未产生真实 DLR 事件，不能报告“数据库实测每事件大小”。

| 持续接管速率 | 每天事件数 | 一份 Envelope 每天/7 天 | 30 天去重行数 |
| --- | --- | --- | --- |
| 0.01 条/秒 | 864 | 3.38 MiB / 23.63 MiB | 25,920 |
| 1 条/秒 | 86,400 | 337.50 MiB / 2.31 GiB | 2,592,000 |
| 10 条/秒 | 864,000 | 3.30 GiB / 23.07 GiB | 25,920,000 |

默认每订阅历史 10,000 项先于 256 MiB 字节限制达到；全局历史 100,000 项先于 1 GiB 字节限制达到。假设空库且没有达到窗口的可清理记录：

| 速率 | 单订阅历史满 | 全局历史满（该总速率） | 目标完全停滞时单订阅 pending 暂停 |
| --- | --- | --- | --- |
| 0.01 条/秒 | 11.57 天（正常终态记录已可按窗口清理，非必然暂停） | 115.74 天（同左） | 30 分钟 oldest-pending 时间门槛先到 |
| 1 条/秒 | 2 小时 46 分 40 秒 | 27 小时 46 分 40 秒 | 16 分 40 秒，1,000 项数量先到 |
| 10 条/秒 | 16 分 40 秒 | 2 小时 46 分 40 秒 | 1 分 40 秒，1,000 项数量先到 |

计算假设无其他订阅/原有责任/控制预留，实际可用容量更低；已有未完或失败屏障受保护时不能靠到期清理解除。默认 7 天原文窗口对应理论平均上限约每订阅 **0.0165 条/秒（0.992 条/分钟）**、全局 **0.165 条/秒（9.92 条/分钟）**；30 天 500,000 项去重限制对应全局约 0.193 条/秒。此为零开销计数上界，不是已达到的完成率，实际执行耗时/Single Adapter Slot、其他 Admission、预留和存储成本可能进一步限制。

因此 1 条/秒运行 30 分钟仅覆盖 1,800 项，可作为短时集成门槛；它不证明按该速度运行七天。10 条/秒仅为有限突发接管上限。当前不放宽历史配额，也不提前缩短 7/30 天承诺窗口。接近容量时应展示可估算的暂停时间并保持背压。

K8s 初始整批 5,000 对象 × 4 KiB 约 19.53 MiB，低于 128 MiB 批次字节限；普通对象之外还要覆盖 3 条各 ≤8 KiB 的控制记录，并在 pending/历史/去重的订阅及全局限制内不可抢占地预留。每批 5,000 项会消耗约半个订阅历史数量预算；两个批次加控制事件已超过 10,000 项，七天窗口内不能靠不停重开大批次恢复，必须在启动时检测剩余额度。此处不要求整轮 5,000 项驻留内存或同时占满 1,000 项 pending。

## 实现后必须复测

1. B1 验证共享原子 quota、取消/续租/旧 owner fence、超时与默认池隔离；客户端参数和 native 线程/内存预算在 B2/B4 绑定真实版本。
2. B3 用实际 DLR Control/Worker、短且幂等的 Adapter、真实 Kafka 与独立目标读回，执行 1 条/秒 30 分钟及 10 条/秒有限突发；同时记录精确 SHA、版本、开始/结束数据库大小、WAL/日志增长、pending/Execution/Outbox 和业务完成率。
3. 缩小数量/字节/历史限制，触限后持续观察 10 分钟；确认 RSS/原生缓存有界、API 无资源耗尽、p95 ≤ 基线两倍，恢复后按序排空。按实测每事件增量重新计算每日/7/30 天磁盘及默认暂停时间。
4. B5 用真实 K8s 分页 LIST/WATCH，分别测客户端额外 RSS、控制预留、超大批次中止和失败后排空/重开；不能把本 socket 探针当作 Kafka native buffer 或 Kubernetes JSON 解码开销证明。
